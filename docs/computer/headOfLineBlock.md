# 队头阻塞

不同版本的 http 都有 `队头阻塞` 问题，不同版本的队头阻塞都不相同

## http 1.1
http 1.1 引入持久连接和流水线传输功能，允许单个 tcp 连接上同时发送多个请求

虽然客户端可以同时发送多个请求，但是服务器必须按照收到请求的相同顺序来发送响应（响应报文本身并不携带“我是回复哪一个请求”的 ID 字段。客户端（如浏览器）分辨响应归属的唯一依据，就是它们到达的顺序）。服务器只有处理完一个 response 才会处理下一个，如果某一个 response 耗时很长，后续响应都需要等待，这就是 http 1.1 中的队头阻塞，发生在应用层

## http 2
http 2 引入多路复用和帧、流的概念，并且只有一条 tcp 连接，服务器同时发送的多个帧，可以不是同一个流，具体如何发送流，由 "http 2" 的优先级系统驱动

### 流(stream)
一个流对应一次完整的请求-响应交换。因为有了流 ID 作为显式配对依据，服务器不再需要按请求顺序返回响应，可以按自己的节奏甚至乱序发送不同流的帧。正是这一点，直接解决了 HTTP/1.1 因为没有请求 ID，顺序是唯一配对依据；HTTP/2 有了流 ID，顺序就不再是必要条件了

### 帧(frame)
帧是 HTTP/2 通信的最小单位，每个帧头都携带所属的流 ID。一个 HTTP 请求或响应，是由同一个流 ID 下的一系列帧“拼”出来的

以一次典型的请求/响应为例：
HEADERS 帧：携带请求或响应的头部字段（经过压缩）。如果头部很大，一个 HEADERS 帧装不下，后面会跟着一个或多个 CONTINUATION 帧来接力
DATA 帧：携带消息主体（body）。一个大的 body 会被拆成多个 DATA 帧发送
结束信号：通过标志位（Flag）来标记消息的结束。例如，带有 END_STREAM 标志的帧，表示该流上不会再有新的数据了

在同一个流内，帧的发送顺序是有意义的，接收方必须按照收到的顺序来处理。逻辑上也是固定的：必须先有 HEADERS（定义请求/响应），才能有 DATA（传输主体）

虽然 http 2 解决了 http 1.1 的队头阻塞，但这也只是解决了应用层阻塞的问题，在传输层 tcp 中，如果出现了丢包，同样会阻塞 http

tcp 协议传输字节流，使用滑动窗口（Sliding Window）机制来实现流量控制和拥塞控制，当出现丢包时，滑动窗口不移动，需要重新传输丢失数据包的副本，滑动窗口中已经到达的tcp包会等待未到达的包

假设一条 HTTP/2 连接上有 stream1、stream2 两条流，TCP 传输中丢了一个包，恰好属于 stream2。TCP 把这一切都看作无差别的有序字节流，并不知道 stream1、stream2 的区别。此时 stream1 的数据其实已经到达接收方的 TCP 接收缓冲区，但由于 TCP 保证按序交付，在属于 stream2 的缺失字节被重传补齐之前，内核不会把缺失点之后的任何数据交给 HTTP/2 层。于是 stream1 只能陪着 stream2 一起等重传，TCP 层的队头阻塞就这样传导到应用层，造成 HTTP/2 上本不相关的流也被阻塞


:::tip
优先级系统驱动
* 公平多路复用（例如两个渐进的 JPEGs）：12121212
* 加权多路复用（2是1的两倍）：22122122121
* 反向顺序调度（例如2是密钥服务器推送的资源）：22221111
* 部分调度（流1被中止且未完整发送）：112222
:::

## http 3
TTP/3 是基于 QUIC 协议的下一代 HTTP 协议。QUIC（Quick UDP Internet Connections）是一种基于 UDP 的传输协议

HTTP/3 用的 QUIC 改变了这一点：QUIC 在传输层就原生支持多路复用，并且能区分不同的流。当丢包发生时，QUIC 知道具体是哪个流的数据丢了，它只阻塞那一个流，其他流的数据可以照常交付给应用层。用你的场景来说：丢的是 stream2 的包，那么 stream1 的数据就可以正常继续往上走，不用再等 stream2 重传了。

:::tip
因为 http 3 将流、帧下放到了 QUIC 协议中，所有 QUIC 能够识别到流、帧，在发生某一个流丢包时，不相关的流继续传输不会阻塞
